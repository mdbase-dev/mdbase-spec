# mdbase v0.3.0 Release Record

## Status and scope

On 2026-11-15, Callum selected plain SemVer instead of further release
candidates. Specification 0.3.0 freezes main at
`47d257d6a56e34c7279e5ebb959af0b0f49744b2` (the untagged rc.6 draft), confirms
its provisional choices, and applies the previously promised rejection of
nondeterministic type matching. The rc.5 and rc.6 changelog content is retained
under the dated 0.3.0 release. Collections still use `spec_version: "0.3.0"`.
There will be no intermediate rc.5 or rc.6 release. New normative work belongs
in backward-compatible 0.3.x errata or 0.4.

This is a specification release, not a declaration that the whole ecosystem
is conforming or released. The former ecosystem-wide gates are explicitly
deferred in the changelog. In particular, the deprecated `mdbase-rs` engine is
not an authority or a release gate. The authoritative implementation is
`mdbase-dev/mdbase-connect`'s `runtime/` workspace. Its current gaps, including
adapter limitations, are recorded in [conformance-0.3.0.md](./conformance-0.3.0.md).
It must not claim stable conformance just because this specification is tagged.

Companion profiles keep their own versions: `merge/0.1`,
`move_detection/0.1`, `type_packs/0.1`, `event_action_interop/0.1`, and
`runtime/0.2`. Their independent qualification is not implied by 0.3.0.

## Stable promises

The thirteen provisional choices are confirmed by removing their markers,
without changing their rules:

| Chapter | Confirmed choice |
| --- | --- |
| 02 | Path safety rule set |
| 02 | Resolving a discovered `path_collision` group by renaming |
| 02 | Full case folding in path keys |
| 02 | Unicode 17.0.0 data for NFC and case folding |
| 03 | YAML scalar resolution table |
| 04 | Data contract view failures are single-record failures |
| 06 | JSON Schema `pattern` uses the mdbase regex profile, not ECMA-262 |
| 07 | `enforce: write` applies at every validation level |
| 07 | RFC 8785 JSON number representation in path values and uniqueness keys |
| 07 | Path-stored fields are strings; FORMAT tokens are `YYYY`, `MM`, `DD` |
| 10 | Insertion-order map iteration in CEL comprehensions |
| 12 | `add` and `remove` address top-level fields only |
| 12 | `body_edits` offsets are Unicode scalar values |

The promised `nondeterministic_match` escalation is applied in chapters 07,
10, 13, and 14 and in `tests/v0.3/cel/match-determinism.yaml`. Invalid types
are excluded from matching. Queries retain time-dependent bindings. The two
changed tests preserve their IDs and original `since:` markers and add
`changed: 0.3.0`; the checker accepts stable release markers.

Type matching uses only the collection's configured `settings.timezone`, never
an invocation timezone or a local-runtime default. Without a configured timezone,
`today()`, `date(timestamp)`, and `startOfDay(string)` in `match.expr` produce a
`nondeterministic_match` error that invalidates the type and excludes it from
matching. A configured timezone does not permit clock-dependent `today()`.
Chapters 10 and 11 and the matching fixtures record this stable decision.

The old requirements for verified claims by every named implementation, an
rc.6 tag, registry-install and multi-platform qualification, and a complete
ecosystem rollout are not claimed complete. The changelog explicitly defers
product qualification because the specification freeze and downstream product
releases are now separate. Historical rc.5 release notes are marked as such.

## Post-merge tagging and publication

No tag or registry publication is part of this PR. After merge, use the exact
merged main commit for every tag and package, following the rc.4 release
precedent (version fields and lockfiles committed before tagging):

1. Create and push `v0.3.0` at the merged release commit. This triggers
   `.github/workflows/ci.yml` and `.github/workflows/deploy.yml` ("Build tagged
   specification artifact"). The latter uploads
   `mdbase-spec-site-v0.3.0`; it does not deploy the product website.
   `mdbase-dev/mdbase.dev` owns importing and deploying the reader.
2. Create and push `mdbase-interop-v0.1.0`. The existing
   `.github/workflows/publish-npm.yml` validates the tag/version, tests and
   inspects the package, checks the version is unpublished, then publishes
   `@callumalpass/mdbase-interop@0.1.0` to npm with `--access public --tag latest`.
3. After interoperability publication succeeds, create and push
   `mdbase-runtime-v0.2.0` and `mdbase-testbed-v0.1.0` at that same commit.
   The same workflow publishes `@callumalpass/mdbase-runtime@0.2.0` and
   `@callumalpass/mdbase-testbed@0.1.0` to npm as `latest`. It builds the local
   interop dependency before testing either package. Do not tag the private
   packages, alter workflow trust, or publish a release candidate.
4. From the same tagged revision, run
   `cargo publish --locked --manifest-path packages/interop-rs/Cargo.toml`
   to publish `mdbase-interop@0.1.0` to crates.io. There is no crate-publishing
   workflow in this repository; the interop tag already identifies its source.
   Do not invent another workflow or imply that the npm tag publishes the crate.

The existing npm workflow selects `latest` for plain versions and `next` for
prereleases; no workflow change is required. Registry credentials and the
protected `npm` environment remain under their existing approval policy.
