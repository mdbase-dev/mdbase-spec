**Sections:** §3 Records and Frontmatter, §8 Links, §9 Lifecycle, §11
Querying, §12 Operations

**Issue:** A review of rc.5 and the rc.6 draft against the mdbase-next Core
found eight rules that the text left to the implementation. Each one changes
stored data or a visible result, so two conforming tools could disagree on
the same collection:

1. `slugify` was "a slug of another field's value" with no algorithm.
2. Simple wikilinks matched filenames, but the text did not say whether
   `[[Alice]]` matches `alice.md`.
3. The closing frontmatter delimiter was not defined, so `...`, `--- `, and
   an unclosed block were open questions.
4. Markdown link destinations had no grammar: percent-encoding, angle
   brackets, titles, and external URLs.
5. Inline tags had no grammar: `#123`, `# Heading`, URL fragments, and which
   characters end a tag.
6. The write order appeared in Chapters 05, 09, and 12 with different
   steps, and none said which path freezes type membership on a create
   whose path is derived.
7. `order_by` said how to compare values of one kind but not values of
   different kinds, and Core had moved the final tie-break from the path to
   the record ID.
8. Normalizing a path-stored value changes what the user typed, such as
   `Plan: Q3/Q4` to `Plan Q3Q4`, and nothing told the caller.

**Resolution (0.3.0-rc.6):**

1. Chapter 09 gives the four steps of `slugify`. It has no transliteration
   table, because a table is a second thing every tool would have to copy
   exactly.
2. Chapter 08 compares targets with paths and filenames by path key. IDs
   stay exact.
3. Chapter 03 defines both delimiters by their bytes. Only a line that is
   exactly `---` closes frontmatter, so a tool finds the end of frontmatter
   without parsing YAML.
4. Chapter 08 defines the two destination forms and decodes only `%20`.
5. Chapter 08 defines the tag grammar and one rule for code in the body,
   shared by link and tag extraction. It is a stated subset of CommonMark,
   so a tool needs no Markdown parser.
6. Chapter 12 holds the only copy of the write order and defines the
   membership path of a create.
7. Chapter 11 adopts Core's order of kinds and keeps `file.path` as the
   final tie-break. A path is in every result row and a record ID is not,
   so a caller can check and continue a path-ordered page without engine
   state. Core returns to path ties.
8. Chapter 07 adds the `path_value_normalized` warning to the result of the
   write.

**Conformance impact:** fixtures marked `since: 0.3.0-rc.6` under requirements
`lifecycle.slugify`, `links.path_key_matching`,
`links.markdown_destinations`, `links.body_code_and_tags`,
`core_read.frontmatter_delimiters`, `core_write.create_membership_path`,
`cel_query.value_order`, `cel_query.path_tiebreak`, and
`core_write.path_value_normalized`.
