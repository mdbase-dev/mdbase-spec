**Sections:** §7 Path Policy, §12 Operations

**Issue:** Collections often keep a field's value only in the path: TaskNotes
stores task titles as filenames, and Obsidian daily notes store the date only
in the filename. v0.3 could derive a path from field values
(`collection.path.pattern`) but not read a value back from a path, so every
client decoded and renamed in its own code (TaskNotes through a `titlePolicy`
contract binding and `collection.path` keys the engine ignored). SN-056 asked
for filename-derived values through v0.2 `generated: {from: file.name}`, which
v0.3 does not have, and left parsing, renames, and cycles open.

**Resolution (0.3.0-rc.6):** `collection.path.fields` declares path-stored
fields. Supersedes SN-056 for filename-derived values.

1. The pattern is decoded against the record's path: anchored, placeholders
   taking the shortest text from left to right, `{field:FORMAT}` date
   occurrences combining their `YYYY`, `MM`, and `DD` components.
2. Decoded values are persisted values for validation, queries, CEL, links,
   lifecycle, and contracts, but never for type matching, which avoids the
   cycle SN-056 noted.
3. Stored fields are never written to frontmatter. Writes normalize the
   value, derive the path after lifecycle, fail with `path_conflict` rather
   than suffix a taken path, and move the record when an update changes the
   value; a rename sets the values from the new path.
4. Other `collection.path` keys load with an `unknown_path_key` warning.

SN-056's directory-derived values (`file.folder`) and slugs remain out of
scope: a pattern's placeholders never contain `/`, and patterns do not
slugify.

**Conformance impact:** `tests/v0.3/core/path-fields.yaml`, requirements
`collection_semantics.path_stored_fields` and `core_write.path_stored_writes`.
